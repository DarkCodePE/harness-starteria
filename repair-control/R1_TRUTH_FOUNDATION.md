# R1 — Truth Foundation Repair Contract

**Repair ID:** `R1`  
**Status:** Ready for implementation after R0 validation-environment check  
**Baseline commit:** `5ff32f9`  
**Branch:** `repair/mvp-r1-truth-foundation`

---

## 1. Objective

Build the minimum transversal truth layer required for Starteria to distinguish:

```text
Claim
  ≠
Evidence
  ≠
Validation
```

and to represent confirmed blockers / attention needs as durable domain state.

R1 must create shared semantics that can later be consumed by:
- Adaptive Core checkpoints
- Decision Center
- Portfolio/Home
- import/publication
- impact/readiness

R1 is not a full evidence-management product.

---

## 2. Why This Repair Exists

The baseline audit found that Starteria can store and display information, but important claims can still exist without a sufficiently explicit contract describing:
- where the claim came from;
- what evidence supports it;
- whether that evidence was validated;
- by whom;
- when;
- what the validation allows the system to conclude;
- whether the item should block progression or trigger attention.

This prevents Steps and Decisions from using evidence as a reliable gate.

---

## 3. Baseline Root Causes

### RC-EVID-01
Evidence is broadly represented as metadata / attachments / provenance fragments, but not as a consistently verifiable domain object that gates progression and decisions.

### RC-BLOCK-01
A confirmed blocker is not represented as one durable shared domain object with enough operational information.

### RC-DATA-01
Persisted backend state coexists with mocks, fallbacks and local UI state in relevant pilot surfaces.

---

## 4. Baseline Critical Gaps Addressed

R1 directly addresses or lays the foundation for:
1. evidence does not govern gates or decisions;
2. blocker / AttentionItem is not a durable domain object;
3. mocks, fallback and local state coexist with backend truth;
4. impact can be presented without sufficiently explicit validation state;
5. AI can consume information whose source/validation semantics are ambiguous.

R1 does **not** itself close GP-B, GP-C or GP-A. It provides the shared layer required to close them.

## 7. Target Domain Semantics

Exact naming may adapt to established repository conventions, but the following concepts must exist explicitly.

### 7.1 SourceRef
Represents where information originated.

Minimum semantics:
- `id`
- source type
- reference / location
- actor or system origin when known
- captured timestamp
- optional content hash/version when applicable

### 7.2 Claim
Represents an assertion used by Starteria.

Minimum semantics:
- `id`
- subject/object reference
- claim type
- statement/value
- source reference(s)
- created by
- created timestamp
- current verification state

A claim must not become validated merely because it was entered by a user or generated by AI.

### 7.3 Evidence
Represents material supporting or contradicting a claim.

Minimum semantics:
- `id`
- source reference
- target claim/object
- evidence type
- captured timestamp
- optional excerpt/metadata
- provenance
- status

Evidence may support, contradict or be insufficient.

### 7.4 Validation
Represents an explicit evaluation of evidence/claim.

Minimum semantics:
- `id`
- claim/evidence target
- result
- validated by
- validator role/type
- timestamp
- rationale
- version

Minimum result semantics should distinguish at least:
- unvalidated
- supported
- contradicted
- insufficient

### 7.5 AttentionItem / Blocker
Represent an operational item requiring attention.

Minimum semantics:
- `id`
- initiative / relevant object
- category
- reason
- severity
- source
- responsible / owner when known
- created timestamp
- status
- exit condition
- next action
- resolution timestamp when closed

A blocker must be durable and queryable; it cannot exist only as local component state.

### 7.6 ImpactStatus
R1 only requires minimum semantics separating:
- declared
- estimated
- validated
- realized

Do not build advanced attribution or benefit tracking.

## 8. Core Business Rules

- **TRUTH-001:** A user or AI statement is a Claim, not automatically Evidence.
- **TRUTH-002:** Evidence must preserve source/provenance.
- **TRUTH-003:** Validation must be attributable to an actor/system rule and timestamp.
- **TRUTH-004:** AI cannot label a claim as validated without a valid validation state.
- **TRUTH-005:** A contradicted or insufficient claim cannot satisfy a gate that explicitly requires validated support.
- **TRUTH-006:** Missing evidence must remain missing; it must not be silently invented or substituted by a mock.
- **TRUTH-007:** A confirmed blocker must persist and remain visible after refresh.
- **TRUTH-008:** Closing a blocker requires explicit resolution state, not merely removing it from a UI list.
- **TRUTH-009:** Pilot primary flows must not silently fall back to mock/local-only state.
- **TRUTH-010:** Impact semantics must not conflate declared/estimated value with validated/realized impact.

---

## 9. Pilot Data Policy

### Allowed
- explicit empty state;
- explicit unavailable state;
- development-only fixture under an explicit dev/test path;
- deterministic test fixture inside tests.

### Not allowed in pilot primary surfaces
- silent mock replacement when API fails;
- local-only decision/blocker truth presented as persisted;
- fabricated evidence;
- generated “validated” status without a real validation event;
- stale fallback represented as current backend state.

---

## 10. E2E Target Scenarios

### Scenario A — User claim without evidence
1. user states an impact/result;
2. claim is stored;
3. no supporting evidence exists;
4. state remains unvalidated;
5. downstream consumer can determine that the claim must not unlock a validation-required gate.

### Scenario B — Supporting evidence
1. claim exists;
2. source-backed evidence is attached;
3. authorized actor/rule validates;
4. validation is stored with provenance;
5. refresh preserves state.

### Scenario C — Contradiction
1. claim exists;
2. new evidence contradicts it;
3. validation records contradiction;
4. downstream consumer can detect the contradiction.

### Scenario D — Confirmed blocker
1. blocker is created against an initiative;
2. source, severity, next action and exit condition exist;
3. reload occurs;
4. blocker remains queryable;
5. resolution explicitly closes it.

### Scenario E — Backend failure in pilot mode
1. primary screen requests real data;
2. backend fails;
3. app must not silently present a mock as current truth.

## 13. Implementation Strategy

Recommended order:
1. inspect existing evidence/provenance/blocker/fallback models;
2. write current-state mapping;
3. define minimum shared domain semantics using existing conventions;
4. add/extend persistence;
5. add service/domain rules;
6. expose minimum API/DTO capability;
7. adapt one minimal projection to prove durability where appropriate;
8. remove/guard silent pilot fallback relevant to R1;
9. add tests;
10. run tests and document evidence.

Do not begin by changing UI styling.

---

## 14. Required Tests

At minimum create or adapt tests demonstrating:
1. claim without evidence is not validated;
2. evidence retains provenance;
3. validation is persisted and attributable;
4. contradicted evidence remains contradicted;
5. blocker persists across a new read/request;
6. blocker resolution is explicit;
7. invalid/insufficient evidence cannot satisfy a validation-required rule;
8. pilot-mode primary data access does not silently substitute mock truth;
9. impact status cannot promote declared/estimated directly to realized without explicit transition.

Where integration tests are feasible, prefer them over only isolated unit tests.

---

## 15. Definition of Done

R1 implementation is technically complete only when:
- minimum Claim/Evidence/Validation semantics exist in code and persistence;
- source/provenance is queryable;
- blocker/attention state is durable;
- pilot mock/fallback rule is enforced for R1-relevant surfaces;
- impact-state minimum distinction exists;
- required tests execute successfully or failures are classified with evidence;
- no KEEP capability was unnecessarily rebuilt;
- no R2/R3/R4 feature was expanded beyond required interfaces;
- implementation report is generated.

This does **not** mean the audit controls are automatically PASS.

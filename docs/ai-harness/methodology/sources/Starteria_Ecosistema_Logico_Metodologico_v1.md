# Starteria - Ecosistema logico y metodologico

**Version:** 1.0  
**Proposito:** describir como se conectan producto, metodologia, contexto, inteligencia artificial, gobernanza, evidencia y decisiones dentro de Starteria.

## 1. Tesis del sistema

Starteria es un sistema para traducir una intencion, problema, oportunidad, proyecto o portafolio en una unidad de trabajo clara, sustentada, ejecutable y gobernable.

No opera como un formulario lineal ni como un unico framework de innovacion. Opera como un ecosistema adaptativo con una columna vertebral estable y capas que ajustan profundidad, preguntas, metodos, validadores y outputs.

```text
Intencion o informacion existente
        +
Contexto organizacional aplicable
        ↓
Extraccion sustentada de hechos y fuentes
        ↓
Interpretacion provisional y preguntas criticas
        ↓
Confirmacion humana del entendimiento
        ↓
Diagnostico de unidad, reto, ruta, dificultad e incertidumbre
        ↓
Seleccion metodologica proporcional
        ↓
Core adaptativo Step 0-4
        ↓
Evidencia, validacion y control de cambios
        ↓
Readiness, decision, handoff e impacto
        ↓
Aprendizaje organizacional reutilizable
```

## 2. Capas del ecosistema

| Capa | Nombre | Funcion principal | Output sistemico |
|---|---|---|---|
| 0 | Gobernanza y seguridad | Define autonomia de IA, confidencialidad, permisos y acciones que requieren validacion | Politica de operacion |
| 1 | Contexto organizacional | Recupera estrategia, estructura, procesos, herramientas, politicas, cultura y antecedentes aplicables | Context Pack relevante |
| 2 | Sustentacion epistemica | Separa declarado, extraido, inferido, sugerido, desconocido, contradictorio y confirmado | Grounded Context |
| 3 | Smart Entry | Entiende que quiere llevar a cabo el usuario y detecta faltantes criticos | Interpretacion provisional |
| 4 | Scope y granularidad | Determina si el input es tarea, iniciativa, proyecto, programa, objetivo o portafolio | Unidad de trabajo confirmada |
| 5 | Routing multidimensional | Clasifica tipo de reto, ruta, profundidad, horizonte y naturaleza de incertidumbre | Route & Depth Profile |
| 6 | Orquestador metodologico | Selecciona lentes, Method Packs, preguntas, evidencias, rubricas y validadores | Method Configuration |
| 7 | Core Step 0-4 | Desarrolla toda iniciativa mediante cinco decisiones permanentes | Outputs versionados por Step |
| 8 | Evidencia y sensemaking | Organiza fuentes, patrones, triangulacion, hallazgos y contraevidencia | Evidence & Insight Map |
| 9 | Gobernanza humana | Asigna validacion al rol con autoridad o conocimiento | Validaciones y escalaciones |
| 10 | Valor y decision | Evalua impacto, inversion, readiness, riesgo y siguiente paso | Decision Brief / Handoff |
| 11 | Memoria organizacional | Conserva aprendizajes, decisiones, activos y patrones reutilizables | Knowledge & Learning Base |

## 3. Columna vertebral Step 0-4

| Step | Decision que debe quedar sustentada | Pregunta central | Output base |
|---|---|---|---|
| 0. Alinear | El punto de partida es entendible y gobernable | Que necesitamos lograr, por que importa y bajo que condiciones? | Context, Route & Method Brief |
| 1. Fundamentar | El foco tiene evidencia suficiente para actuar | Que ocurre, para quien, por que y con que evidencia? | Focus Definition + Evidence & Insight Map |
| 2. Disenar | Existe una ruta de accion ejecutable y medible | Que haremos con los recursos, restricciones y tiempo disponibles? | Test Card, Solution Card, Roadmap o Gantt |
| 3. Contrastar | La realidad produjo resultados y aprendizajes interpretables | Que ocurrio, que senal aparecio y que debemos ajustar? | Execution, Evidence & Learning Record |
| 4. Transferir | Existe una decision y una salida organizacional responsable | Que debe hacer ahora la organizacion, quien lo recibe y como se medira? | Decision Brief, Handoff Pack o Closure Plan |

## 4. Clasificaciones que no deben confundirse

| Clasificacion | Pregunta que responde | Valores base |
|---|---|---|
| Tipo de reto | Que valor busca mover? | correction, growth, exploration |
| Tipo de ruta | Que trabajo necesita hacer ahora? | explore_validate, design_solution, implement_handoff, plan_coordinate, reconstruct_existing, lightweight_plan |
| Unidad | Que objeto se esta creando? | tarea, iniciativa, proyecto, objetivo, reto, programa, portafolio |
| Profundidad | Cuanto rigor requiere? | light, standard, systemic |
| Naturaleza | Cuanto es conocido o incierto? | algorithmic, mystery, mixed |
| Horizonte estrategico | Que distancia existe frente al negocio actual? | H1, H2, H3, unconfirmed |
| Estado metodologico | En que decision esta? | Step 0-4 |
| Readiness | Que tan preparada esta para su siguiente transicion? | low, medium, high, not_evaluable |
| Evidencia | Que tan sustentadas estan las afirmaciones? | initial, partial, sufficient, validated, conflicting |

## 5. Jerarquia de objetos

```text
Organization / Program
└── Strategic Front
    └── Challenge
        └── Initiative
            ├── Context Versions
            ├── Step Progress 0-4
            ├── Evidence
            ├── Method Configuration
            ├── Validation
            ├── Blockers
            ├── Value Case
            ├── Readiness Assessment
            ├── Decision
            └── Handoff / Learning
```

Una iniciativa independiente puede existir sin frente o reto, pero debe registrar la justificacion de independencia. En Portfolio Lead, una iniciativa publicada debe estar asociada a un frente/reto o permanecer explicitamente por clasificar.

## 6. Estados epistemicos de la informacion

| Estado | Uso |
|---|---|
| declared | El usuario lo afirmo explicitamente |
| extracted | Aparece en una fuente identificable |
| inferred | La IA lo dedujo y debe presentarlo como provisional |
| suggested | La IA propone una alternativa o formulacion |
| unknown | No existe informacion suficiente |
| conflicting | Existen datos incompatibles |
| confirmed | Un actor autorizado valido el dato o interpretacion |
| outdated | La informacion perdio vigencia |

**Regla madre:** ningun dato critico inferido se convierte en contexto confirmado sin validacion humana.

## 7. Resolucion del contexto organizacional

```text
Organizacion
  + Unidad de negocio
  + Area
  + Proceso/producto/servicio
  + Frente y reto
  + Iniciativa
  + Capacidad real del usuario/equipo
        ↓
Context Resolver
        ↓
Seleccion de fuentes vigentes, permitidas y relevantes
        ↓
Deteccion de contradicciones y vacios
        ↓
Preguntas al usuario
```

El contexto mas especifico prevalece sobre el general cuando tiene fuente valida y vigencia. Las contradicciones se muestran; no se resuelven silenciosamente.

## 8. Orquestador metodologico

El Orquestador recibe el perfil diagnosticado y activa un conjunto limitado de Method Packs.

### Inputs

- ruta confirmada;
- tipo de reto;
- profundidad;
- naturaleza de incertidumbre;
- Step actual;
- contexto organizacional;
- evidencia disponible;
- nivel de riesgo;
- output solicitado;
- rol del usuario;
- validadores requeridos.

### Outputs

- preguntas activadas;
- actividades sugeridas;
- evidencias minimas;
- lente o framework seleccionado;
- rubrica de calidad;
- hard gates y soft gates;
- validador humano;
- artefacto final.

### Method Packs iniciales

- Context & Alignment;
- Scope & Decomposition;
- Process Discovery;
- Qualitative Research;
- Iceberg/Systemic Diagnosis;
- Market/Segment Exploration;
- HMW & Ideation;
- Service Design;
- Test Card;
- Implementation Roadmap;
- Gantt & Coordination;
- Adoption & Handoff;
- Learning Card;
- Decision Brief;
- Executive Narrative.

## 9. Gobernanza por rol

| Incertidumbre o decision | Rol principal |
|---|---|
| Calidad metodologica | Mentor |
| Realidad del reto o proceso | Challenge Owner |
| Prioridad y cobertura de portafolio | Portfolio Lead |
| Presupuesto, continuidad o escalamiento | Sponsor / Comite |
| Datos y definiciones | Data Owner |
| Arquitectura, integracion y seguridad | TI / Arquitectura / Riesgos |
| Operacion futura | Area receptora |
| Ejecucion cotidiana | Initiative Owner |

La IA identifica el dominio de incertidumbre y recomienda el rol; no inventa personas ni asigna autoridad.

## 10. Gating

### Hard gates

- objetivo o unidad de trabajo no confirmados;
- owner inexistente para un compromiso;
- violacion de linea roja;
- contradiccion critica no resuelta;
- decision o aprobacion obligatoria ausente;
- intento de escalar sin evidencia critica;
- cambio de contexto que invalida outputs posteriores.

### Soft gates

- baseline estimado;
- sponsor pendiente;
- evidencia parcial;
- dependencia secundaria no confirmada;
- presupuesto preliminar;
- datos que pueden obtenerse en el siguiente Step.

Los soft gates permiten continuar con alerta, supuesto visible y tarea de regularizacion.

## 11. Ciclos de retroalimentacion

1. **Context loop:** nuevo contexto puede reabrir clasificacion o Steps.
2. **Evidence loop:** nueva evidencia fortalece, contradice o invalida una hipotesis.
3. **Execution loop:** resultados de Step 3 pueden iterar Step 2 o reformular Step 1.
4. **Portfolio loop:** aprendizajes de iniciativas cambian retos, cobertura o prioridades.
5. **Learning loop:** decisiones y handoffs alimentan la memoria organizacional.
6. **AI quality loop:** aceptaciones, ediciones y rechazos mejoran rubricas y golden datasets.

## 12. Pseudocodigo del sistema

```text
function process_input(user_input, attachments, user, workspace):
    context = resolve_relevant_context(user, workspace, user_input)
    grounded_facts = extract_with_sources(user_input, attachments, context)
    ambiguities = detect_route_changing_ambiguities(grounded_facts)

    if ambiguities.critical:
        ask_up_to_three_questions(ambiguities)

    interpretation = build_provisional_interpretation(grounded_facts)
    require_user_confirmation(interpretation)

    if not interpretation.confirmed:
        do_not_create_official_initiative()

    unit = classify_unit(interpretation)
    challenge_type = classify_challenge_type(interpretation)
    route = classify_route(interpretation)
    depth = classify_depth(interpretation, context)
    uncertainty = classify_mystery_algorithm(interpretation)
    horizon = suggest_horizon_if_corporate_context_exists(interpretation, context)

    require_confirmation_for_decisional_classifications()

    methods = orchestrate_methods(
        route, depth, uncertainty, challenge_type, context, evidence
    )

    create_snapshot_and_workspace()
    configure_steps_0_to_4(methods)
    execute_current_step_with_grounded_outputs()
    route_human_validation_by_domain()
    preserve_versions_evidence_and_decisions()
```

## 13. Regla de simplicidad

La complejidad interna del ecosistema no debe trasladarse como carga al usuario. Starteria debe mostrar:

- que entendio;
- que no puede confirmar;
- que pregunta es critica;
- que ruta recomienda;
- que sigue;
- por que solicita una validacion.

Los frameworks y rubricas operan principalmente como arquitectura interna.
